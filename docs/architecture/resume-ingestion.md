# Resume Ingestion Architecture

## 1. Overview

InterviewIQ implements a production-grade resume ingestion pipeline focused on secure upload authorization, content magic byte validation, deterministic storage key generation, immutable versioning, tenant-scoped duplicate detection, and asynchronous background job handoff.

---

## 2. Ingestion Workflow Architecture

```
HTTP Upload Request (PDF / DOCX)
              │
              ▼
[1. Authorization & Tenant Validation]
 ├── Verify Active Organization Context & Member Permissions (candidate:update)
 └── Verify Active Candidate Profile
              │
              ▼
[2. File & Signature Validation]
 ├── Check Maximum Size (<= 10 MB)
 ├── Validate Extension (.pdf or .docx)
 ├── Inspect Magic Bytes (b"%PDF-" or b"PK\x03\x04")
 └── Calculate SHA-256 Checksum
              │
              ▼
[3. Tenant-Scoped Duplicate Detection]
 └── Query active ResumeORM in (candidate_profile_id, checksum_sha256)
              │
              ▼
[4. Version Calculation & Deactivation]
 ├── Version = max(existing_versions) + 1
 └── Deactivate Previous Versions (is_active_version = False)
              │
              ▼
[5. Storage Upload & DB Persistence]
 ├── Write to StorageProvider (organizations/{org_id}/candidates/{cand_id}/resumes/{resume_id}/v{version}/filename.pdf)
 ├── Insert ResumeORM (processing_status: QUEUED, is_active_version: True)
 ├── Create BackgroundJobORM (job_type: RESUME_PARSING, status: QUEUED)
 └── Emit Audit Event (resume.uploaded)
```

---

## 3. Storage Key Strategy

File object keys are generated by the server and decoupled from user-controlled input:

`organizations/{organization_id}/candidates/{candidate_id}/resumes/{resume_id}/v{version_number}/{sanitized_filename}`

Original filenames are stored only as database metadata in `ResumeORM.original_filename` to prevent path traversal and object enumeration.
